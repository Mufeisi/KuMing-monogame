# 暂不执行物理目录重排

- 状态：已取代
- 日期：2026-08-12
- 决策人：项目所有者
- 关联任务：ENG-09
- 取代者：[`ADR-0037`](0037-物理目录采用分批迁移.md)

## 背景

仓库顶层同时存在客户端、服务端、共享库、启动器、微端、测试、工具和发布目录，视觉上不符合新建项目常见的 `src/`、`Tests/`、`Tools/` 布局。但工程已长期运行，构建、资源、发布与文档大量依赖当前相对路径。

2026-08-12 盘点得到：

- 30 个有效工程已经全部进入主解决方案，并按 9 个逻辑目录分类；
- Server、Launcher 与 Windows 三个解决方案过滤器提供子系统入口；
- `Server`、`Shared`、`Build` 等目录名分别出现在 819、237、203 个文件中；
- 工程文件中有 45 条 `ProjectReference`；
- CI、PowerShell、Markdown 中分别至少有 17、13、223 处结构路径引用；
- 模块地图、文档索引和 CODEOWNERS 已解决主要的导航与所有权缺口。

## 决策

当前不把工程批量移动到 `src/`、`Tests/`、`Tools/`，也不为追求目录外观重命名工程或命名空间。

继续使用以下低风险结构表达方式：

1. `Legend of Mir.sln` 的逻辑解决方案目录表达架构分类；
2. `.slnf` 提供 Server、Launcher、Windows 等工作集；
3. [`模块地图.md`](../guides/模块地图.md) 维护职责、依赖、入口和验证；
4. [`.github/CODEOWNERS`](../../.github/CODEOWNERS) 维护审查责任；
5. CI 保证磁盘工程与主解决方案集合一致。

## 理由

- 物理迁移不会自动形成更深的模块接口，也不会减少核心类复杂度；
- 大量相对路径、资源路径、发布脚本和历史文档会产生高噪声 diff，回归面远大于导航收益；
- Git 历史追踪和多人分支合并成本会显著增加；
- 当前逻辑分类已经让开发者与 Agent 无需依赖顶层目录猜测职责。

## 重新评估条件

只有同时满足以下条件时，才创建独立迁移 PR：

1. 计划中的新顶层结构能消除一个已量化的开发或发布问题，而非只改善观感；
2. 全部工程、脚本、CI、资源、文档和部署路径可由现有门禁完整枚举；
3. 迁移可拆为小批次，每批均能构建、测试并独立回滚；
4. 活跃功能分支已经收口，避免大面积合并冲突；
5. Windows、Server、Launcher、Android 发布和资源基线均有可执行迁移前后对照。

若未来实施，优先先移动低耦合 `Tools` 或 `Tests` 子集验证流程，不从 `Server`、`Shared`、`Build` 或客户端资源目录开始。

## 影响

短期保留顶层目录较多的外观，但避免无业务价值的高风险路径改写。模块化改善继续通过真实功能触达时的深模块提取（ENG-08）完成，而不是以文件搬家替代接口设计。

## 取代说明

2026-08-12 后续复核确认：根目录的源码模块平铺与本地产物目录共同造成了可观察的导航负担，且首轮治理已建立工程集合、文档链接、协议清单和三平台 CI 门禁，满足本文的重新评估条件。原“禁止一次性全盘迁移”的理由仍有效，但“当前完全不迁移”的决定由 ADR-0037 取代。
