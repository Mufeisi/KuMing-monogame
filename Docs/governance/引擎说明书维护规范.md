# LyoCrystal 引擎说明书维护规范

- 状态：已接受
- 负责人：项目所有者
- 最后复核日期：2026-08-15
- 事实源：实际代码、配置、测试和发布清单；说明书源位于 `Manual/Engine/`
- 取代关系：取代“以单一 CHM 文件作为手工事实源”的候选方案

## 1. 目标与载体决定

LyoCrystal 必须提供面向服主、脚本作者和运维人员的产品级引擎说明书，具备清晰分类、中文全文搜索、图文示例、错误排查、版本状态和离线分发能力。

主载体采用 Material for MkDocs 静态说明书站点：Markdown 是唯一内容事实源，构建后输出静态 HTML 和本地搜索索引，可部署到网站或作为 ZIP 离线分发。CHM、PDF 等格式只能从同一事实源派生，不得手工维护内容副本。

## 2. 读者与内容边界

| 读者 | 主要问题 | 内容入口 |
|---|---|---|
| 新服主 | 如何安装、配置、启动和验证 | 快速开始、服务器配置 |
| 脚本作者 | 能用什么命令、参数和变量 | 脚本开发、命令参考、示例 |
| 玩法开发者 | 如何组合系统能力 | 功能系统、配方教程 |
| 运维人员 | 如何诊断、备份、迁移和回滚 | 运维、数据库、故障排查 |
| 版本升级人员 | 新增、变更、废弃了什么 | 版本说明、兼容与迁移 |

说明书只描述用户可观察行为，不承载内部实现计划、未确认推测、秘密、生产数据或商业第三方说明书原文。内部设计继续位于 `Docs/design/`。

## 3. 信息架构

一级分类固定如下，新增一级分类必须审查导航是否已有合适位置：

1. 欢迎与快速开始；
2. 安装、目录与服务器配置；
3. 脚本开发；
4. 人物、物品、怪物、地图和任务系统；
5. 客户端、界面和资源；
6. 数据库、持久化和数据迁移；
7. 运维、诊断、安全和发布；
8. 命令、变量、配置和错误代码参考；
9. 版本说明、兼容矩阵和废弃项。

每页只回答一个主要用户问题。导航使用业务词，不使用内部类名；内部标识符放在语法和参考部分。页面标题、别名和自定义搜索词应覆盖用户常用称呼。

### 3.1 页面布局

页面采用大型技术产品说明书常见的稳定三栏结构：

- 顶部：产品标识、一级分类、全局搜索、浅色/深色切换；
- 左侧：当前分类的分级目录，并突出当前页面；
- 中间：限宽正文，保持每行适合连续阅读；
- 右侧：当前文章目录，长页面可快速跳转；
- 底部：上一篇/下一篇和相关页面。

首页使用任务型卡片，不按内部代码模块堆砌入口。功能页优先显示状态、版本、用途和最小示例，再展开参数、错误和高级场景。代码示例提供复制按钮；警告、危险、兼容和提示采用稳定视觉层级，不只依赖颜色表达含义。

视觉风格使用 LyoCrystal 自有标识、色彩和 SVG，不复制 Microsoft Learn、GitHub Docs、Stripe 等公司的商标、图标或页面代码。参考的是信息层级与可用性模式，而非品牌外观。

## 4. 页面标准

每个功能或命令页面必须包含适用项：

1. 功能状态：规划中、实验性、已实现、已废弃；
2. 首次支持版本、适用平台和权限要求；
3. 用途与典型场景；
4. 前置条件和生命周期；
5. 语法；
6. 参数、类型、范围、默认值和单位；
7. 返回值、可观察结果和副作用；
8. 至少一个最小示例和一个真实组合示例；
9. 失败行为、错误代码和排查；
10. 安全、性能、持久化和兼容注意事项；
11. 相关页面；
12. 页面复核版本。

示例必须可以复制，不能使用省略号隐藏必要上下文。规划功能必须在页面首屏明确标注“当前版本不可用”，不得混入已发布命令参考。

## 5. 图文标准

- 截图必须来自实际版本，裁掉账号、IP、路径、密钥和人物隐私信息。
- 图片使用 PNG/WebP，架构和流程优先使用可审查的 SVG；必须有中文替代文字和图注。
- 一张图只解释一个核心关系；分辨率保证 125% Windows 缩放下可读。
- 动图和视频必须同时提供文字步骤，不能成为唯一操作说明。
- 图片放在对应主题目录的 `assets/`，使用相对链接；禁止外链易失图片作为唯一证据。
- 发布前检查浅色/深色主题、桌面/窄屏和打印可读性。

## 6. 搜索与术语

- 搜索使用简体中文 `zh` 和 jieba 分词。
- `Manual/Engine/search-dictionary.txt` 维护项目专有词，如 `LyoCrystal`、`翎风兼容`、`热重载`。
- 页面标题表达正式术语；别名、旧称和常见错别字写入页面元数据或正文“又称”。
- 命令、变量前缀、错误代码和配置键必须可被原样搜索。
- 每次发布抽查至少 15 个中文业务词和 10 个代码标识符，首屏结果必须能到达正确页面。

## 7. 功能完成门禁

任何新增或改变用户可见行为的任务，必须同批完成：

1. 代码与配置；
2. 自动测试和必要运行证据；
3. 对应说明书页面；
4. 导航、交叉链接和搜索词；
5. 版本状态与变更说明；
6. `mkdocs build --strict`；
7. 若功能影响升级或数据，迁移和回滚页面。

缺少说明书不得标记功能完成、合并或发布。纯内部重构若可观察行为完全不变，可以不新增页面，但必须确认现有页面仍准确。

## 8. 审查职责

| 审查者视角 | 必须确认 |
|---|---|
| 开发 | 命令、参数、默认值和错误与代码一致 |
| 测试 | 示例可执行，边界和失败行为有覆盖 |
| 产品/服主 | 分类、术语和场景能被目标用户理解 |
| 安全/运维 | 无秘密泄露，风险、备份和回滚清晰 |
| 发布 | 页面状态、首次支持版本和制品一致 |

## 9. 构建、发布与回滚

- 直接依赖记录在 `Manual/Engine/requirements.txt`，经过验证的完整依赖固定在 `requirements.lock.txt`；正式构建使用锁定文件。
- 本地预览使用 `Build-Manual.ps1 -Serve`；正式构建使用严格模式。
- 输出目录是可重建产物，不进入说明书内容事实源。
- 发布包记录源码提交、依赖版本、构建命令和 SHA-256。
- 说明书错误优先修复源 Markdown 并重建；禁止直接编辑生成 HTML。
- 回滚说明书时回滚源码提交并重新构建；已发布旧版本保留可追踪归档。

## 10. CHM 与其他格式

CHM 仅在明确存在 Windows 离线客户需求且具备稳定编译器时增加。它必须由现有 Markdown 自动派生，并通过目录、搜索、图片、中文编码和链接抽查。不得因为 CHM 工具链限制而降低主说明书的搜索、移动端或图文能力。

PDF 适合归档和打印，不承担交互搜索事实源；站点 ZIP 适合内网和离线分发；在线站点适合持续更新。三个制品若同时发布，必须来自同一提交。
