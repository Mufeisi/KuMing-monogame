# LyoCrystal 工程开发规范

- 状态：已接受
- 负责人：项目所有者
- 最后复核日期：2026-08-12
- 通用执行基线：`standard-software-engineering`
- 上位规则：`AGENTS.md`、当前 PRD、已接受 ADR

本文规定 LyoCrystal 后续功能、修复、优化、工程治理和发布工作的统一生命周期，不复制动态开发进度。工程治理状态以 `工程治理实施路线.md` 为唯一事实源；产品任务状态以开工时明确指定的活动 PRD、Issue 或实施规格为唯一事实源。`PRD-PC稳定与Android发布.md` 已完成并转入维护，只保存 P0～P5 历史验收事实，不再作为当前任务队列。

本规范参考 Google Engineering Practices 的小变更与代码健康原则、Microsoft Engineering Fundamentals、GitHub 的受保护分支与必需检查、NIST SSDF、OWASP ASVS 及 Google SRE 的发布和无责复盘实践。它们提供方法基线；本仓库的具体约束仍以上述优先级为准。

## 1. 规则强度与优先级

### 1.1 优先级

1. 用户明确指令与验收标准；
2. 安全、隐私、生产和数据保护；
3. 当前 PRD 与 GATE 退出条件；
4. 已接受且仍有效的 ADR；
5. `AGENTS.md`；
6. 本规范与通用技能；
7. 局部习惯和个人偏好。

### 1.2 强度

- `MUST`：违反时不得合并或宣称完成。
- `SHOULD`：原则上遵守；偏离必须记录理由和剩余风险。
- `MAY`：根据任务上下文采用。

## 2. 任务生命周期

### 2.1 准入（MUST）

开工前必须提交任务简报，包含：目标、用户价值、做、不做、方法约束、风险等级、预估时间、完成定义、验证、回滚、语言。

完成定义必须对应可运行代码、测试输出、截图、制品或可复核对比数据。纯分析、计划、矩阵和报告不构成功能完成。

### 2.2 现状检查（MUST）

- 阅读适用的 `AGENTS.md`、PRD、ADR、模块文档和本文。
- 检查分支与工作区，列出并保护已有未提交修改。
- 查找现有实现、测试与接缝，禁止重造已有能力。
- 确认本任务对应的 GATE、文件所有权和唯一事实源。
- 协议、线程、脚本、渲染、数据库与发布必须遵守 `AGENTS.md` 红线。

### 2.3 设计（按风险）

跨模块、难回滚或涉及协议、Schema、线程、安全、发布拓扑的变更必须先形成设计。设计至少包含：接口、数据流、不变量、失败模式、兼容、迁移、验证与回滚。

只有影响系统结构、关键质量属性或难以逆转的决定才新增 ADR。一个 ADR 只记录一个决定；设计接受与代码实施必须使用不同状态。

### 2.4 实现（MUST）

- 一个任务只解决一个主要目标，范围外问题进入 backlog。
- 功能变更不得混入全局格式化、无关升级和机械重命名。
- 优先形成小接口、深实现的模块；不要以 `partial` 或层层转发伪装模块化。
- 接受依赖，不在深处隐式创建难替换的外部依赖。
- 修改协议只改 `src/Shared/Shared/` 事实源并更新 manifest、兼容测试和消费者。
- 数据库改表必须走 `SchemaMigration`；发布与运行数据遵循备份和恢复约束。
- 用户可见中文、文档、状态和提交信息使用中文；代码标识符和原始报错可保留英文。

### 2.5 验证（MUST）

按风险执行最小充分验证：

1. 格式、静态检查和生成物漂移；
2. 受影响工程构建；
3. 相关单元测试；
4. 集成测试；
5. 协议、Schema、配置或版本兼容测试；
6. 必要的手工、设备、端到端或制品验证。

缺陷修复原则上先建立可失败的回归测试。无法执行的验证必须列明原因、剩余风险和补验入口；不得写成“已通过”。单次验证预计超过 30 分钟时遵守 `AGENTS.md` 的快慢内外环规则。

### 2.6 审查与合并（MUST）

审查顺序为：规格、总体设计、正确性、安全/数据/并发、兼容、测试、可读性、文档、发布和回滚。

意见分为：阻断、应改、建议、细节。技术事实和项目规范高于个人样式偏好。

任务完成验证后必须显式询问是否合并；不同任务保持独立分支与提交，不在长生命周期分支持续堆叠。

## 3. 模块与工程结构

- 每个工程或重要模块必须能说明职责、非职责、接口、错误模式、所有者和测试入口。
- 新模块必须有真实消费者；新接缝必须对应真实变化或测试适配需求。
- 解决方案、过滤器和磁盘工程必须同步；新增工程时同步更新适用的 `.sln`、`.slnf` 与 CI。
- 公共 SDK、编译规则和确需统一的包版本逐步收口到仓库级配置；不以一次性大迁移阻塞当前 GATE。
- 巨型类按完整行为闭环渐进提取深模块，先建立行为回归，禁止按固定行数拆文件或大爆炸重写。

## 4. 测试与质量门禁

| 变更 | 最低门禁 |
|---|---|
| 纯规则 | 单元测试 + 受影响构建 |
| 数据库/文件/网络 | 集成测试 + 失败路径 |
| 协议/配置/Schema | 契约或兼容测试 + 漂移检查 |
| UI/设备行为 | 自动化探针或截图/设备证据 + 相关构建 |
| 性能 | 变更前基线 + 同环境对比 |
| 安全 | 威胁对应测试 + 秘密/日志/失败关闭检查 |
| 发布 | 实际制品冒烟 + 摘要/签名 + 回滚验证 |

测试必须断言模块接口上的可观察行为，不穿透内部实现。CI 结果必须对应待合并的最新提交。

## 5. 安全、数据与发布

- 秘密、令牌、生产密码、私钥和个人信息不得进入源码、普通配置、Git、日志、测试快照或 AI 输出。
- 高风险能力使用安全默认值；验证失败时关闭，不静默降级。
- Schema 迁移必须声明兼容窗口、备份、恢复与不可逆部分。
- 发布物必须可追踪到提交、SDK、依赖、测试、版本、摘要和签名。
- 正式发布验证实际制品，不以开发目录运行替代；发布后必须检查关键路径与回滚阈值。

## 6. 文档治理

### 6.1 唯一事实源

| 事实 | 唯一来源 |
|---|---|
| 工程治理状态 | `工程治理实施路线.md` |
| 当前产品任务与 GATE | 开工时明确指定的活动 PRD、Issue 或实施规格；当前未指定活动产品 PRD |
| P0～P5 历史验收 | `PRD-PC稳定与Android发布.md`；不得解释为当前任务队列 |
| 长期架构决定 | `Docs/adr/` 中已接受且未被取代的 ADR；`继续开发架构设计报告.md` 仅为历史审计基线 |
| 项目执行铁律 | `AGENTS.md`、`执行纪律与防走偏铁律.md` |
| 领域术语 | `CONTEXT.md` |
| 实际行为 | 代码、配置与测试 |
| 协议 | `src/Shared/Shared/` C# 源码；生成 manifest 只做审计 |
| 构建与验证 | 构建配置、CI 和 `Docs/Evidence/` 原始证据 |
| 发布和运维 | RELEASE、OPS、SEC 专项文档及实际制品 |

### 6.2 文档职责

- README：项目定位、快速开始、入口导航；不维护完整动态进度。
- PRD：用户目标、范围、验收和门禁；不承载详细实现教程。
- ADR：一个架构决定；不维护任务流水账。
- 设计/实施规格：具体方案、失败模式、测试和迁移。
- Evidence：执行时证据和结论快照；历史状态不回写成动态事实。
- Runbook：部署、诊断、恢复和回滚操作。

新增长期文档应标记状态、负责人、最后复核日期、事实源和取代关系。旧文档先在 `Docs/index.md` 标注职责与状态，再渐进整理；禁止为了整齐一次性移动全部文档。

文档状态至少使用“草案、已接受、已实施、已完成并转入维护、已废弃、已取代”之一。文档中的过程记录按原时间语境保留；若其中出现“进行中”“仍未完成”等表述，必须由文档头部生命周期说明或索引明确其为历史截面，禁止批量改写历史证据制造伪同步。

## 7. 交付格式

每次交付至少说明：

- 实现了什么以及用户入口；
- 关键文件或制品；
- 实际运行的验证及结果；
- 未验证项和剩余风险；
- 是否涉及部署、迁移或回滚；
- 是否请求合并。

## 8. 自动化路线

以下规则应按后续独立任务逐步进入 CI，不在文档治理任务中顺带实现：

1. `.sln`/`.slnf` 与磁盘工程一致性；
2. 文档内部链接与状态元数据；
3. 协议和生成清单漂移；
4. 秘密、依赖漏洞、SBOM 与许可证；
5. PR 模板、CODEOWNERS、分支保护和必需状态检查；
6. 发布制品来源、摘要、签名与回滚证据。
