# DB-02 后台保存快照与代次

## 保存契约

SQLite 运行期保存继续复用 DB-01 的唯一写线程和既有数据域快照工厂。调用线程先完成快照捕获，再把快照所有权交给 `ImmutableSaveSnapshot<TSnapshot>`；信封不暴露载荷，后台写线程只能通过提交回调读取。快照工厂必须创建与 `Envir`、玩家、账户、行会等可变游戏对象脱离的 DTO，交接后调用线程和游戏主线程均不再修改该 DTO。

这里的“不可变”是保存边界的所有权约束：DTO 由快照工厂一次性填充，交接后由信封独占，并非宣称每个既有 DTO 类型都只有语言级只读属性。账户专项测试在交接后、事务排空前修改在线账户金币，数据库仍写入交接时的旧值，证明后台事务没有回读可变游戏对象。

MySQL 保存仍保持原有同步路径；DB-02 不改变 MySQL 事务模型，也不引入新的数据库表或 SchemaMigration。

## 保存代次

每次 SQLite 快照捕获前分配进程内全局单调递增代次。唯一写线程按数据域记录最高已接受代次，并拒绝等于或低于该值的迟到请求，防止旧快照覆盖新快照；只有事务成功时才推进该数据域的最后成功提交代次，失败事务不会伪报成功。

世界、关系、账户、行会、商品与攻城属于完整域快照。同一域尚未开始的多个请求可由更高代次替换为最新快照；已经开始的事务不会被替换。角色归档属于逐角色增量写入，同域多项必须逐项提交，因此明确关闭待处理合并，但仍受单调代次检查保护。

代次是单进程写线程的并发顺序护栏，不作为跨重启持久版本号。进程退出后旧写线程与内存队列一起终止，新进程从新代次开始；跨重启的备份版本、RPO 与恢复语义分别属于 DB-03～DB-05。

## 持久性与度量

SQLite 每个正式连接显式设置 `PRAGMA synchronous = FULL`，并继续使用 WAL、私有连接缓存和 5 秒 `busy_timeout`。

两段耗时沿用已有性能指标并明确其边界：

- `SaveSnapshotCapture`：调用线程执行快照工厂的耗时；
- `SaveTransactionCommit`：后台写线程打开事务、写入并提交的耗时。

专项测试验证两次账户保存分别产生两条捕获样本与两条提交样本，并验证捕获线程是调用线程、提交线程是唯一后台写线程。

## 阶段边界

DB-02 不实现在线备份、恢复演练、备份保留与异地副本，不改变 `SaveDelay` 生产强校验，也不定义 MySQL 切换门槛。这些工作继续由 DB-03～DB-06 承担，GATE-P3 不因 DB-02 完成而关闭。
