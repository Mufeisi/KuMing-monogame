## 1. 当前基线

2026-08-12 只读核验：远端仓库 `Mufeisi/KuMing-monogame` 的默认分支为 `main`，分支保护 API 返回 `Branch not protected`。本地新增的 CI 检查尚未在远端产生检查记录，因此不得提前把不存在的上下文设为必需检查。

仓库内治理工件：

- [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)：统一范围、风险、验证、文档、发布和回滚信息；
- [CODEOWNERS](../.github/CODEOWNERS)：默认责任人及协议、服务端、数据库、安全、发布、客户端、启动器和微端等高风险边界；
- [`base-03-ci.yml`](../.github/workflows/base-03-ci.yml)：构建、测试、协议生成物、工程集合和文档链接门禁。

## 2. `main` 目标规则

在 GitHub Ruleset 或 Branch protection 中对默认分支配置：

1. 合并前必须通过 Pull Request，不允许直接推送；
2. 至少 1 个批准，要求 Code Owner 审查，提交更新后撤销旧批准；
3. 必须解决全部会话；
4. 必需检查必须来自最新提交，启用严格分支同步；
5. 禁止强制推送和删除分支；
6. 规则同时作用于管理员，仅通过有审计记录的临时 bypass 处理紧急恢复；
7. 不强制线性历史，允许团队按任务选择 squash 或保留有意义的独立提交。

首轮 CI 成功后，从 GitHub 已产生的检查上下文中选择以下三个 job 作为必需检查，不手工输入猜测名称：

- `Windows build (solution filter)`；
- `Android Release arm64 AOT publish`；
- `General tests (discovered projects)`。

文档链接、解决方案工程集合及 Windows 专项测试属于第一个 job；协议清单与通用测试属于第三个 job。任一 job 失败都必须阻止合并。

## 3. 应用与验证

1. 按正常发布流程将包含本文件的提交推送到远端任务分支；
2. 创建 PR，确认模板自动出现且 CODEOWNERS 自动请求 `@Mufeisi`；
3. 等待三个 CI job 在 PR 最新提交上成功运行；
4. 由仓库管理员按第 2 节应用 `main` 规则；
5. 新建一个无代码的验证 PR，确认缺少批准、缺少 Code Owner 审查或任一检查失败时无法合并；
6. 更新本文状态为“已应用”，记录规则链接、应用日期和验证 PR。

规则应用属于远端状态变更，不由普通源码任务顺带执行。若仓库升级为多人维护，先建立 GitHub Team，再将高风险路径从个人账号迁移到团队所有权，避免单点审查瓶颈。

## 4. 紧急变更

生产事故仍需独立分支、最小 diff、验证证据和回滚方案。确需 bypass 时必须记录原因、操作者、时间范围和事后补验；恢复后立即撤销临时权限，不将紧急流程变成日常入口。
