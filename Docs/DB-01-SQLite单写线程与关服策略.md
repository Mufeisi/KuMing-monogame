# DB-01 SQLite 单写线程与关服策略

## 生效范围

SQLite 连接使用 WAL、私有连接缓存和 5 秒 `busy_timeout`。连接打开时先读取当前日志模式，仅在数据库尚未处于 WAL 时执行切换，避免并发读连接重复争用日志模式写锁。MySQL 与 Legacy 路径不改变。

运行期 SQLite 保存复用现有各数据域快照：游戏主线程先捕获不再读取可变玩家状态的快照，再把事务提交动作交给唯一后台写线程。写线程同时只执行一个事务；同一数据域尚未开始的多个请求只保留最新快照，不同数据域按首次入队顺序执行。已经开始的事务不会被替换，其间到达的同域请求形成下一次待提交快照。

本任务覆盖世界、世界关系、账户、行会、商品、攻城与角色归档的运行期保存。启动加载阶段已有的迁移、补种和回填仍保持同步，因为它们发生在服务进入运行态之前。

## 关服顺序

SQLite 正常关服按以下顺序执行：

1. 把最终账户、行会、商品和攻城快照投递到服务主线程捕获；
2. 等待唯一写线程完成正在执行的事务和各域最后一次待提交事务；
3. 检查既有 `SqlSaveResilience` 连续失败策略；达到配置阈值时取消本次关服并保持服务运行；
4. 通过失败检查后在同一主线程回调内冻结运行态，当前帧立即退出；资源清理不再追加商品保存；
5. 保存恢复成功后可再次关服；工作循环不会重复提交已完成的最终保存。

事务继续复用既有最多 3 次瞬时错误重试、失败告警、失败日志、自动保存冷却和关服阻止策略。`DrainPendingSaves` 只表示队列已经排空；最终是否允许关服由连续失败状态决定。

## 验证与阶段边界

T-09 覆盖专用线程、最大并行写数为 1、同域 100 次待处理请求合并、队列排空等待，以及真实 WAL 写事务进行时 8 个并发读取任务无死锁。生命周期测试覆盖四个最终快照在主线程捕获、排空发生在停服之前，以及保存失败取消关服、恢复后重试成功。

DB-01 不引入保存代次，也不宣称完整后台保存语义已经收口。不可变快照契约、单调保存代次、`synchronous=FULL` 默认值和两阶段耗时口径仍属于 DB-02；在线备份和恢复属于 DB-03/04。
