## 1. 目标与用户价值

版本作者可以在既有专业作者工具中设计安全的游戏内窗口，以同一份经过签名和版本约束的运行描述在 PC 与 Android 显示，并最终以一个活动兑换窗口完成服务端权威业务闭环。作者不需要手写坐标或运行时代码，客户端也不能决定奖励、价格、物品归属或玩家状态。

## 2. 任务简报

- 目标：依次关闭 `GATE-GUI-CORE`、`GATE-GUI-STATIC`、`GATE-GUI-DYNAMIC`，交付一个可设计、可验证、可发布、可回滚的双端自定义游戏窗口闭环。
- 用户价值：版本作者复用成熟画布工作流生产游戏窗口；玩家在 PC 与 Android 获得一致体验；业务结果由服务端权威验证。
- 做：设计核心深化、游戏 GUI Schema、作者 Adapter、PC/移动运行 Adapter、签名与资源限制、服务端窗口会话、白名单动作、状态投影及活动兑换纵向闭环。
- 不做：通用脚本 UI、任意反射/文件/URL 调用、客户端权威奖励、重写 FairyGUI、重写 `DXManager`/`SpriteBatchStack`、重写协议序列化、商城/交易/强化等第二业务场景。
- 方法约束：每个切片独立分支、提交、测试和证据；上一门禁未关闭不得进入下一门禁；优先复用现有签名资源、微端、渲染与协议接缝。
- 风险等级：高。涉及跨端运行描述、签名输入、资源上限、协议边界和玩家状态权威性。
- 预估成本：12～20 人周；这是阶段拆分依据，不是发布日期承诺。
- 完成定义：同一签名 GUI 包在 PC 与 Android 正确显示并由服务端打开、投影、处理白名单动作和关闭；篡改、过期、未知类型、越界资源与重放均失败关闭；一个活动兑换窗口完成真实双端验收。
- 验证方式：无 UI 领域测试、作者工具 Windows 集成、PC/Android 运行适配测试、协议兼容与攻击样例、签名/降级/资源上限测试、真实双端截图或录屏及测试服业务冒烟。
- 回滚方式：按独立切片回滚代码；客户端 GUI 包按已接受序列和签名版本回退；动态窗口由服务端 Kill Switch 停用并关闭现有会话；Schema/协议一旦进入兼容窗口按专项迁移说明处理。
- 语言：全部交流、规格、状态、证据与提交信息使用中文。

## 3. 当前基线与真实接缝

1. 启动器作者画布的当前事实实现为 `src/Launcher/Launcher.Editor/LauncherCanvasDocument.cs`；选择、几何变换、吸附、对齐、层级、锁定、隐藏、撤销/重做和脏状态已经通过真实 UI 消费。
2. `LauncherCanvasDocument` 当前位于 WinForms 项目，并直接依赖启动器 `LauncherTheme`/`LauncherControlId` 文档模型；它是 `GATE-GUI-CORE` 要渐进深化的对象，不得与新核心长期双轨存在。
3. PC 渲染必须走现有 `DXManager`/MirControls 接缝；移动渲染必须复用内嵌 FairyGUI 与 `SpriteBatchStack`。Adapter 只映射运行描述，不复制渲染器。
4. GUI 包签名、摘要、防降级、主备源和原子切换复用现有 Bootstrap 清单与接受策略；不建立第二套信任根或下载器。
5. 动态协议只允许在静态门禁关闭后，于 `src/Shared/Shared/Packet.cs` 的现有序列化体系中增加真实包；服务端玩家状态仍只由主线程修改。

## 4. 实施顺序

### 4.1 `GATE-GUI-CORE`：设计核心深化

1. `GUI-CORE-01` 设计核心基线与接缝审计：固定当前启动器行为契约、依赖边界、公共接口、迁移顺序和回归入口；当前活动切片。
2. `GUI-CORE-02` 深模块提取：将文档、选择、命令、几何、历史、诊断和变更通知移入不引用 WinForms、FairyGUI、MonoGame 或 Vortice 的项目。
3. `GUI-CORE-03` 启动器 Adapter 接回：对象树、画布、属性检查器仅通过核心接口修改文档，删除旧窗体内部重复逻辑。
4. `GUI-CORE-04` 内存 Adapter 与门禁：设计行为测试只断言公共可观察结果，现有 `GATE-UXL` 行为和截图无回归。

`GATE-GUI-CORE` 退出条件以专项路线为准：启动器无回归、核心无 UI/渲染依赖、测试只走接口、旧逻辑不与新核心并存。

### 4.2 `GATE-GUI-STATIC`：双端静态窗口

1. `GUI-01` 游戏 GUI 设计文档和运行描述 Schema：首版只包含 `Window/Panel`、`Image`、`Text/RichText`、`Button`、`TextInput`、`List`、`ProgressBar`、`ItemSlot` 及专项路线规定的布局能力。
2. `GUI-02` 作者工具游戏 GUI Adapter，复用设计核心和既有三栏工作区，不增加新的永久平级侧栏。
3. `GUI-03` PC Adapter，通过现有 `DXManager` 与 MirControls 映射静态控件。
4. `GUI-04` 移动 Adapter，通过现有 FairyGUI 与 `SpriteBatchStack` 映射同一运行描述。
5. `GUI-05` 资源、字体、图集、安全区、数量、层级、文本与总包大小校验；未知控件、未知属性、循环引用和超限资源失败关闭。
6. `GUI-06` 静态“新手活动窗口”双端显示与签名发布冒烟。

### 4.3 `GATE-GUI-DYNAMIC`：服务端权威活动窗口

1. `GUI-07` Shared 真实协议包与严格上限。
2. `GUI-08` 服务端窗口会话、GUI 版本绑定、随机数和重放保护。
3. `GUI-09` 主线程验证动作、文本、选择、物品所有权、距离、NPC、活动、货币和次数。
4. `GUI-10` PC/Android 状态投影和有界增量更新。
5. `GUI-11` 脚本旁路 Hook，只允许声明窗口、提供数据和处理登记的白名单动作。
6. `GUI-12` 一个活动兑换窗口完成 PC/Android/服务端真实闭环。

## 5. 不变量与失败模式

1. 同一设计文档只能生成确定版本的运行描述；构建与运行不得各自解释一套语义。
2. 客户端只提交动作意图和受限输入，不提交价格、奖励结果、权威物品属性或次数结论。
3. 每个动作绑定玩家、窗口实例、GUI 版本、会话随机数和有效期；未知、过期、乱序或重放请求必须拒绝。
4. 所有列表、文本、资源、控件数、嵌套深度、包体和协议载荷都有显式上限；解析失败不得降级为任意运行。
5. GUI 包只有通过现有信任链、签名、摘要、兼容版本和防降级校验后才能加载；发布失败保留上一已接受版本。
6. PC 和 Android Adapter 不拥有业务状态，不绕过现有渲染接缝，不在后台线程修改玩家状态。
7. 设计核心只拥有编辑行为，不拥有启动器主题、游戏 GUI Schema 或运行时控件类型；这些由各自 Adapter 映射。
8. 保存、发布和版本切换使用临时输出、完整校验和原子替换；失败必须可重试且不破坏原事实。

- 设计核心领域测试及依赖边界检查。
- `Launcher.PlayerShellIntegration.Windows` 作者行为回归。
- Shared Schema/签名/上限测试。
- PC 与移动 Adapter 的相同运行描述投影测试。

### 6.2 阶段外环

- `GATE-GUI-CORE`：启动器真实画布与四档 DPI 无回归。
- `GATE-GUI-STATIC`：同一签名 GUI 包在 PC 与 Android 显示标题、图片、列表、进度和按钮；保存双端截图与诊断样例。
- `GATE-GUI-DYNAMIC`：测试服服务端打开活动兑换窗口，双端完成一次合法兑换；篡改、重放、过期、断线重连和版本切换全部有明确结果及日志证据。

证据按切片写入 `Docs/Evidence/LEG-07-YYYYMMDD/`；Evidence 只记录执行事实，不承担动态状态。

## 7. 阶段退出条件

1. `GATE-GUI-CORE`、`GATE-GUI-STATIC`、`GATE-GUI-DYNAMIC` 依次关闭，且无越级实现或长期双轨核心。
2. 版本作者可在作者工具中设计静态活动窗口，无需手写 JSON 或坐标文本。
3. 同一签名运行描述在 PC 与 Android 正确显示，未知或超限输入失败关闭。
4. 一个真实活动兑换窗口由服务端权威完成打开、数据投影、合法动作、拒绝非法动作、更新和关闭。
5. 客户端不能授予奖励、决定价格、伪造物品或绕过次数/距离/活动校验；玩家状态只在服务端主线程修改。
6. 构建、领域测试、Windows 集成、双端运行、安全失败样例、测试服冒烟、截图/录屏和回滚证据全部通过。

## 8. 当前切片 `GUI-CORE-01`

### 做

1. 为现有启动器画布行为建立稳定公共契约和内存测试表面。
2. 确定无 UI 设计核心项目位置、依赖方向和最小接口。
3. 将一个完整行为簇（选择、移动、吸附、撤销/重做）迁移并让启动器 Adapter 接回。
4. 证明核心项目不引用 WinForms、FairyGUI、MonoGame 或 Vortice；证明对应启动器行为无回归。

### 不做

1. 不定义游戏 GUI Schema，不新增游戏控件类型。
2. 不实现 PC/Android 游戏 GUI Adapter。
3. 不修改 Shared 协议、服务端窗口会话或玩家状态。
4. 不建立通用命令框架或第二套启动器主题文档。

### 完成定义

现有启动器画布对“选择→移动/吸附→撤销→重做”的可观察行为不变，行为由无 UI 核心接口承载，旧实现对应逻辑被删除而非保留双轨；领域测试和 Windows 集成均通过，并产生独立代码提交与证据文档。

## 9. 回滚

1. 每个 `GUI-*` 切片独立提交，可按逆序回滚；不得用一次提交跨越两个阶段门禁。
2. `GUI-CORE-*` 回滚必须恢复启动器 Adapter 与核心的匹配版本，禁止留下两套编辑逻辑。
3. 静态 GUI 包通过现有资源版本切换回上一已接受签名版本；客户端遇到不兼容版本失败关闭而非解释旧数据。
4. 动态阶段必须提供服务端 Kill Switch：停止新开窗口并关闭/过期现有会话；代码回滚不得令玩家卡在未完成事务中。
5. 若未来需要 SchemaMigration 或协议兼容窗口，必须在对应切片独立补充迁移与回滚说明，本激活规格不预先授权数据迁移。
